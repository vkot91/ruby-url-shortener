# The load harness

This directory is a deliverable, not scaffolding. The project's headline claim is a
*measured* difference between a naive read path and a cached one (constitution Principle II),
and a claim like that is only worth the reproducibility of the instrument behind it.

Everything here therefore exists so that two runs, taken weeks apart, differ in the code under
test and in nothing else.

| File | What it is |
|---|---|
| `env.sh` | The reference environment. Sourced by the other two scripts; not run directly. |
| `seed.sh` → `seed.rb` | Creates `shortener_load` and fills it with the fixed 10 000-link corpus (T040). |
| `serve.sh` | Boots the backend with `REDIRECT_CACHE_ENABLED` set to the argument (T042). |
| `worker.sh` | Boots the Sidekiq process that drains the click buffer. Needed for the cached run only (T059). |
| `redirect.js` | The k6 script. Reused **unchanged** for the 3C run — that is what makes it a comparison (T041). |
| `enumerate.js` → `enumerate.sh` | SC-007, first half: absent codes must not reach Postgres (T060). |
| `stampede.js` → `stampede.sh` | SC-007, second half: a hot key expiring must not produce one query per request (T061). |
| `pg_transactions.sh` | Reads Postgres' committed-transaction counter. Both SC-007 checks are claims about the database, not about the client. |
| `corpus.json` | Generated by `seed.rb`, committed. The codes and their popularity ranks, shared with `redirect.js`. |
| `results/` | Committed run output and the written analysis. |

## Running it

Three shells, or two if you background the server.

```sh
cd backend && docker compose up -d      # postgres + redis, as in quickstart.md

./load/seed.sh                          # once; re-runnable, replaces rather than appends

./load/serve.sh false                   # naive path
k6 run -e RESULT=load/results/naive.json load/redirect.js

# restart the server with the flag flipped — it is read once at boot
./load/serve.sh true                    # cached path (Phase 3C)
./load/worker.sh                        # and the click-flush worker, in its own shell
k6 run -e RESULT=load/results/cached.json load/redirect.js

./load/enumerate.sh                     # SC-007: enumeration (T060)
./load/stampede.sh                      # SC-007: hot key expiring (T061)
```

The worker is the one difference between the two runs' *environments*, and it is there to keep
them comparable rather than to make them differ. The cached path has not stopped writing clicks,
it has stopped writing them inside the request (D4); `worker.sh` is where those writes happen
instead, on the same host, competing for the same CPU. Omitting it would credit the cached run
with a throughput it reaches by not doing the work.

`k6 run` must be issued from the repository root: `redirect.js` opens `corpus.json` beside
itself, and `RESULT` is resolved against the working directory.

`BASE_URL` overrides the target (default `http://localhost:3001`).

## The reference environment

The numbers in `results/` were taken on this. Reproducing them elsewhere requires reproducing
this, and a run on different hardware should say so rather than being compared directly.

| | |
|---|---|
| Host | Apple M3 Pro, 12 cores, 36 GB, macOS 26.4.1 — everything co-resident (research.md D13) |
| Backend | Ruby 3.4.8, Rails 8.0.5, Puma, `RAILS_ENV=production`, single worker, `RAILS_MAX_THREADS=5` |
| Postgres | `postgres:17` in Docker (Docker 27.4.0), published on 5433, database `shortener_load` |
| Redis | `redis:7.4` in Docker, `maxmemory 512mb`, `allkeys-lru`, published on 6380 |
| Load generator | k6 v2.2.0, on the same host |
| Corpus | 10 000 links, seed `20260901`, Zipf exponent 1.07 |

Four of those choices are load-bearing and should not be quietly changed between runs:

- **Production mode, not development.** Development reloads code, stats files on every request,
  and carries the debug-exceptions and server-timing middleware. A baseline measured through
  those would describe Rails' development conveniences, and the 3C run would then take credit
  for removing them. `config.force_ssl` needs no working around, because `config.assume_ssl` is
  also on — nothing in the application is modified to run this.
- **`RAILS_MAX_THREADS=5`, left alone.** `backend/.env` says outright that the small pool is
  there so the naive path's queueing shows up in the baseline instead of being tuned away.
  Raising it for the run would tune it away in the one place it matters.
- **Co-residency.** k6, Puma, Postgres and Redis on one host removes network variance, at the
  cost of the load generator competing for CPU with the thing it measures. At the top steps
  that competition is real and is noted in the analysis.
- **A Zipf draw, not a uniform one.** Uniform access across 10 000 links would understate the
  cache in 3C by a factor real traffic never produces. Short-link traffic is a handful of posts
  drawing most of the clicks; `s = 1.07` is the exponent usually fitted to web popularity.

## How the run is shaped

`redirect.js` offers a fixed request rate for 30 seconds, then a higher one, through
`500 → 1000 → 2000 → 4000 → 6000 → 8000` requests per second. Each step is its own k6 scenario
carrying a `step` tag, so every metric in the committed summary is reported per step.

That shape is the point of the exercise. An aggregate over a run that degrades describes
nothing — a p99 averaged across a healthy 500/s and a saturated 8 000/s is not a fact about
either — whereas the per-step table shows the rate at which the service stopped keeping up,
which is what "where it broke" means.

Two properties of the request follow from `contracts/redirect.md` and are asserted on every
iteration rather than sampled:

- `maxRedirects: 0`. k6 follows redirects by default, which would send every VU out to
  `example.com` and measure the internet. It also hides the 302, the `Location`, and the
  `Cache-Control` this request exists to check.
- The `Location` must equal the destination the corpus says belongs to that code. SC-005 asks
  for zero incorrect destinations, which is unmeasurable if the check is only "did it 302".

An **open** workload (`constant-arrival-rate`), not a closed one: SC-004 is phrased as a rate
the service sustains, so the offered rate has to be the independent variable. With a fixed pool
of VUs a saturated server simply slows every VU down and throughput flattens at whatever the
server felt like doing.

## Why the result file is a summary, not `--out json`

`quickstart.md` shows `k6 run --out json=load/results/naive.json`. That flag writes one line per
metric sample — gigabytes for a run this size, unreadable and uncommittable. `redirect.js`
exports `handleSummary` instead and writes the same numbers at per-step granularity to the path
in `RESULT`. The committed artifact is a file a reviewer can open.

## Costs worth knowing before you run it

- The naive path inserts a click row per redirect, so a full baseline leaves several hundred
  thousand rows in `shortener_load`. That is why the corpus has its own database and why
  `seed.sh` clears the clicks: it keeps the mess out of `shortener_development` and stops one
  run's writes from sitting under the next run's reads.
- `seed.sh` is destructive within the `load@snip.test` account only, and creates that account if
  it is absent.
